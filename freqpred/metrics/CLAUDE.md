# Sizing assessor — change and audit workflow

**For any change to the sizing assessor's LLM or its inputs — `_SYSTEM_PROMPT`, `_build_prompt_payload`, `_PROMPT_VERSION` (`freqpred/metrics/assessment.py`), the judgment model (`anthropic.judgment_model`), `assessment_scale_min/max`, or any new/changed data section in the assessment payload:**

- Follow README → "Auditing the sizing assessor". Validate with the paired two-arm screen: `current` = the live production package (needs no setup, it is whatever shipped), `challenger` = the proposed package, defined in the CHALLENGER block at the top of `scripts/audit_assessor_enhancement.py`. Do not adopt on inspection alone — propose the run to the user as the required validation step.
- **Use the frozen eval set, not the reshuffling sample.** Score with `scripts/run_frozen_eval.py` against `scripts/.audit_output/frozen_eval_set.json` (built by `scripts/freeze_assessor_eval_set.py`). The old `_pick_sample` path reshuffles over a pool that grows as assessments accrue, and it is not fit for adoption decisions: the *identical* v6/opus-4-7 package scored corr +0.529 on one draw and +0.246 on the next, so run-to-run differences were sample composition rather than package quality. The frozen set stores rendered payloads plus a hash, so runs are byte-reproducible and harness drift invalidates a cached score instead of silently mixing old scores with new prompts. Regenerate the set only deliberately — it is the frozen baseline, and regenerating it discards every cached `current` score.
- **Adoption gate: capital tilt and incremental AUC over the free prior** (`scripts/.audit_output/analyze_noninferiority.py`), not raw correlation. Capital tilt (mean size multiplier on winners minus losers) is the direct expression of "put more size on winners". AUC is ~2× better powered than Pearson correlation on this data (CI width 0.336 vs 0.622) and is scale-invariant, so it separates ranking quality from calibration. Always read the **incremental-over-prior** line: absolute AUC flatters every arm because most of it is reproducible from a free direction×edge-band lookup — as of 2026-08-09 no assessor package has beaten that lookup (the best increment is GLM-5.2's +0.026, CI −0.038..+0.094), so an arm that merely matches it is not earning its per-signal cost. Also check the verdict distribution: an assessor that never says size_up is a flat tax, not a discriminator.
- Keep `max_tokens` at or above the audited value (**currently 6000, for `z-ai/glm-5.2`**) and keep `trust_score` emitted first in the tool call. A truncated response fails open to neutral 1.0x sizing — a silent loss of the sizing decision rather than a visible error. **The budget is per-model and not transferable:** at 768 a wordier package truncated mid-response; at the 1024 that Opus was audited at, GLM-5.2 spent the whole cap on reasoning tokens and returned a `tool_use` block with `input={}` — no `trust_score` at all, still billed. Re-measure (observed max, p95, calls at cap) whenever the judgment model changes; `scripts/audit_assessor_enhancement.py:CHALLENGER_MAX_TOKENS` sets the challenger arm's budget independently so the incumbent's audited value is untouched during a screen.
- Retrospective audits must use the script's point-in-time loader copies, never the raw production context loaders — on since-resolved markets those self-leak the assessed market's own outcome into the prompt (production is immune; an unresolved market has no outcome to leak).
- Audit calls cost real API dollars (one call per signal per live arm — ~$0.011 on `z-ai/glm-5.2`, ~$0.048 on `claude-opus-5`, so a two-arm 76-signal screen ranges from ~$0.85 to ~$4.50 depending on the arms) and share the daily LLM cap with the live pipeline — check today's spend and confirm the run with the user first. Calls are logged as `query_type="model_eval"`; nothing may ever be written to `signal_assessments` from an audit.
- Bump `_PROMPT_VERSION` (`assessment-vN`) on any adopted prompt/payload change so old and new assessments stay distinguishable in `llm_queries` and `signal_assessments`. **A model-only swap must not bump it** — `model_used` already separates the arms, and bumping orphans the frozen set's `current` cache, which the freezer keys on the version prefix.

**On adoption — the steps after a screen wins.** No challenger was adopted through this harness until 2026-08-09, so these were improvised the first time. Full procedure in README → "Adopting a challenger"; the two that cause silent damage if skipped:

- **Re-harvest the frozen set's `current` cache to the adopted package.** `run_frozen_eval.py` reuses a cached `current` response whenever the **payload** hash matches, and that hash does not change when the system prompt or the model changes — so a cache harvested under the previous package survives adoption and scores the *retired* package as "current" on the next screen, with no error. The v6/opus-4-7 cache did exactly this straight through the v8 adoption. Repoint it from the adoption run's own calls (free), matching on `model_used == anthropic.judgment_model` and `prompt_version LIKE '{_PROMPT_VERSION}%'` by hashing each `llm_queries.prompt` against the stored payload hash. Confirm the payload bytes are unchanged; only the two cache fields may differ.
- **Disarm the CHALLENGER block** and record the screened package plus its result there as a comment. `tests/unit/test_audit_harness.py::TestChallengerIsDisarmedAfterAdoption` enforces this.
